# v1.1 plan: the media server (desktop), built as drop-ins

Status: plan, 2026-10-08. Decisions are the user's (recorded in the brief); the design below is ours. Desktop only: the web app is the lowest
priority and nothing here runs in a browser tab. v1.2 uses the same interface.

## 1. Scope

**v1.1 (drop-ins):** (1) DLNA/UPnP in four roles (browse and play from servers, share our library to TVs, accept "Play To", send to renderers);
(2) a LAN server that serves our web app to phones and browsers, plus a phone remote (PIN pairing, LAN only, off by default); (3) Chromecast
sending; (4) a client for Jellyfin, Subsonic and Navidrome; (5) WebDAV network folders; (6) remux to MP4; (7) our own clean-room encoders
(H.264 and AAC-LC) so the server can transcode, real-time 1080p on desktop as the target.
**v1.2 (same interface):** SMB, internet radio and podcasts, multi-room sync, AirPlay.
**Not in scope:** the browser build, port forwarding or any internet exposure, DRM, "DLNA certified" claims (we say UPnP AV).

## 2. Architecture

```
rvp-host-desktop  (composition root: the only place that names drop-ins; cargo features pick which are compiled in)
   | passes Vec<Box<dyn DropIn>> and a DropInHost implementation to
rvp-app  --- knows only rvp-dropin (the interface), never a drop-in
   |
rvp-ui   --- draws the tabs and a drop-in's ViewSpec; never names a drop-in
rvp-core / rvp-player / rvp-library: unchanged, no dependency on any drop-in
```

* **Tabs.** The Music and Video buttons of the rail become tabs; a new **Server** tab is added when at least one drop-in is enabled. A
  drop-in with a `view()` shows as a section of the Server tab (a list on the left, its page on the right; on a phone a list that opens
  pages). Remote libraries (Jellyfin, Subsonic, WebDAV, UPnP servers) also appear as sources inside Music and Video, because they are
  media; the Server tab holds their connection and sharing settings.
* **Compile time and run time.** A drop-in is a crate behind a cargo feature of `rvp-host-desktop` (`dropin-upnp`, `dropin-lanweb`, ...).
  Whether it is **on** is a setting (Settings > Server), off by default. Off means it is constructed but never `start`ed: no socket, no
  thread, no discovery traffic.
* **Threads.** Drop-ins may use threads and blocking sockets (desktop); the app talks to them with messages only (`DropInEvent` in,
  `DropInCommand` out, polled from `tick`), so a stuck network never stalls the UI thread.

## 3. The drop-in interface (`rvp-dropin`, `no_std + alloc`, interface only)

```rust
pub trait DropIn {
    fn id(&self) -> &'static str;              // "upnp", "lanweb", "cast", "jellyfin", ...
    fn name(&self) -> &str;                    // shown in the Server tab and Settings
    fn icon(&self) -> Icon;                    // from the Unicorn Tears icon set
    fn needs(&self) -> Needs;                  // host capabilities: LISTEN, CONNECT, MULTICAST(ssdp|mdns), FILES_READ, TRANSCODE
    fn settings(&self) -> SettingsSchema;      // typed switches, numbers, text, lists; stored by the app under "dropin/<id>"
    fn start(&mut self, host: &mut dyn DropInHost) -> Result<()>;
    fn stop(&mut self);
    fn tick(&mut self, now_us: i64, host: &mut dyn DropInHost) -> Vec<DropInCommand>;   // play this, add source, toast, ...
    fn event(&mut self, ev: DropInEvent, host: &mut dyn DropInHost);                    // UI actions, now-playing changes, pairing answers
    fn view(&self) -> Option<ViewSpec>;        // declarative page: headings, rows, cards, switches, buttons, text; no drawing code
    fn sources(&self) -> Vec<SourceSpec>;      // remote libraries it offers to Music/Video (browse tree + stream URLs)
}
```

`DropInHost` is what the host grants, each call checked against `needs()` and the user's switch: `listen(addr, kind)`, `connect`, `udp`
(multicast group joins), `library()` (a **read-only** snapshot with opaque ids, never paths), `open_stream(id, range)`, `playback()` (queue,
play, pause, seek, volume, now-playing), `storage()` (namespaced), `transcode()` (the pipeline of section 4), `clock()`, `log()`.
The messages are plain serialisable data so a loadable adapter could be added later without changing drop-ins (see section 9).

## 4. Crates

| crate | role |
|---|---|
| `rvp-dropin` | the interface above, `ViewSpec`, `SettingsSchema`, `Needs` (no_std + alloc) |
| `rvp-net` | std only: HTTP/1.1 server and client (ranges, chunked, keep-alive), WebSocket, SSDP, mDNS/DNS-SD, private-address checks, TLS via a vetted crate (rustls) |
| `rvp-xml` | small XML reader/writer for SOAP, DIDL-Lite, WebDAV; no external parser |
| `rvp-mux` | MP4 (and fragmented MP4 / HLS segments) writer: the remux feature and the transcode output |
| `rvp-enc-h264` | our H.264 encoder; reuses `rvp-codec-h264`'s modular pieces (bitstream, transform, CAVLC/CABAC, intra/inter prediction tables) |
| `rvp-enc-aac` | our AAC-LC encoder (MDCT, window switching later, simple psychoacoustics, rate control) |
| `rvp-transcode` | pipeline demux > decode > scale/convert > encode > mux/segment, with a thread pool and a budget (cores, bitrate); also "copy" paths that skip stages |
| `rvp-dropin-upnp` | UPnP AV: MediaServer (ContentDirectory, ConnectionManager), MediaRenderer ("Play To": AVTransport, RenderingControl), control point (browse servers, send to renderers) |
| `rvp-dropin-lanweb` | serves the web app bundle, the stream endpoints and a WebSocket remote; PIN pairing |
| `rvp-dropin-cast` | Cast v2 sender (CASTV2 protobuf over TLS, hand-written messages), default media receiver, mDNS discovery |
| `rvp-dropin-jellyfin`, `rvp-dropin-subsonic` | clients (Subsonic and Navidrome share the Subsonic API); browse, search, covers, stream URLs, scrobble optional |
| `rvp-dropin-webdav` | PROPFIND/GET-range client exposed as a folder source for the library scanner |
| `rvp-netsource` | the "source over HTTP" the player needs (a `MediaSource` with range reads, caching, reconnect), used by all remote drop-ins |

v1.2 adds `rvp-dropin-smb`, `-radio` (with podcasts), `-multiroom`, `-airplay`, none of which touch the crates above except `rvp-net`.

## 5. Security model

1. **Off by default**, each role separately (UPnP server, UPnP renderer, LAN web, each client). Turning one on shows what it will open
   (ports, discovery) before it starts; turning it off closes everything at once.
2. **Read-only shares.** Only folders the user ticks are shared; content is addressed by opaque ids, never paths (no traversal); no write
   method is implemented in any server role. The tag editor, playlists and settings are never reachable from the network.
3. **LAN only.** Listeners bind to private interface addresses only (RFC 1918, link-local, ULA fc00::/7); every request's peer address is
   checked again and refused if it is not private; no UPnP IGD, NAT-PMP or any port mapping, ever. A VPN or a public interface is not a LAN.
4. **Pairing.** The web server and the remote need a 6-digit PIN shown on the desktop; five wrong tries lock that client for a minute and
   rotate the PIN; a successful pairing gives a 128-bit token (stored hashed), listed and revocable in Settings. Tokens are bound to the
   server instance. DLNA has no authentication: TVs are handled by an allow-list ("Allow Living Room TV?" the first time a device browses),
   and an incoming Play To asks once per controller.
5. **Limits.** Bounded request sizes, header counts, connection counts and transcode jobs; a wrong request costs nothing but a 4xx.
6. **TLS.** The web server is plain HTTP by default on the LAN (with the token); an optional self-signed certificate (trust on first use) is
   offered. See risk R2: a plain-HTTP page is not a secure context, which limits what the served web app can use.
7. **Privacy.** Cast, UPnP and the clients send nothing to the internet except what the user points them at (a Jellyfin server they typed).

## 6. Firewall, ports and per-OS notes

| role | listens | talks |
|---|---|---|
| SSDP (UPnP discovery) | UDP 1900 (multicast 239.255.255.250 / ff02::c) | same |
| UPnP media server / renderer | one TCP HTTP port (default 8200, configurable) | to devices' announced ports |
| mDNS (Cast discovery) | UDP 5353 (multicast 224.0.0.251) | Cast TCP 8009 outbound; the Cast device then fetches media from our HTTP port |
| LAN web and remote | TCP 8765 (configurable) | none |
| Jellyfin / Subsonic / Navidrome / WebDAV clients | none | outbound to the server's port (8096, 4533, 80/443 ...) |

* **Linux:** firewalld usually blocks inbound on `public`: document `firewall-cmd --add-service=ssdp` (or the port) per zone, and have the
  app say when a listener is up but unreachable (a loopback self-test). ufw: `ufw allow from 192.168.0.0/16 to any port 8200,8765 proto tcp`.
  The `.deb`/`.rpm` ship no firewall changes (we never open ports ourselves).
* **Windows:** the first listen shows Defender's prompt; ask for **Private networks only**. The Inno installer may add a private-profile
  rule per executable, opt-in on a checkbox. Multicast needs the right network profile (Private).
* **macOS:** the first listen shows the application-firewall prompt (a signed app is allowed by default); from macOS 15 the **Local Network**
  permission applies, so Info.plist needs `NSLocalNetworkUsageDescription` and `NSBonjourServices` (`_googlecast._tcp`, `_services._dns-sd._udp`).
* **Flatpak:** `--share=network` (already granted for theme links) covers listening and multicast sockets; discovery through Avahi needs
  `--system-talk-name=org.freedesktop.Avahi` only if we use it (we do our own mDNS, so we do not). Folder sharing uses the existing
  `xdg-music`/`xdg-videos`; WebDAV and remote sources need no extra access. Flathub's reviewers will look at network permissions: the manifest
  states why, and the listeners stay off until switched on.
* **AppImage/tar.gz:** no sandbox; nothing to add.

## 7. Test plan

* **CI, no hardware (fake devices on loopback):** in-process fake UPnP server, renderer and control point driven through an injectable
  transport (SSDP over a loopback hub); a fake Cast receiver (TLS server speaking the CASTV2 subset: connect, heartbeat, launch, load, status);
  fake Jellyfin, Subsonic/Navidrome and WebDAV servers serving recorded JSON/XML and a small media file (range requests included).
* **Protocol conformance:** SOAP/DIDL-Lite golden documents checked against the specs' examples; SSDP/mDNS/HTTP/WebSocket parsers fuzzed
  (occasional job, with the user's OK on the shared host); the existing damaged-input style (no panics, bounded memory).
* **Security tests:** path traversal and id guessing, non-private peers refused, PIN brute force lockout, token revocation, request-size limits,
  "off means no socket" (the process opens nothing until a switch is on; verified with a socket listing in a test).
* **Media:** remux output read back by our demuxer and `ffprobe` (same streams, same timestamps); encoders: decodable by our decoders and ffmpeg,
  PSNR/SSIM floors on fixed clips, rate-control accuracy, speed floors on the perf fixtures (single run, not a loop); A/V sync of transcodes.
* **By the user, on real devices (not in CI):** two or three TVs/players for UPnP (browse, play, Play To, seek), a Chromecast and a Chromecast with
  Google TV, an iPhone and an Android phone on the LAN web page and remote, real Jellyfin/Navidrome/Subsonic/WebDAV servers, per-OS firewall
  prompts on Windows and macOS, a Flatpak install.

## 8. Risks

* **R1 Encoder quality and speed.** Real-time 1080p H.264 needs motion search, SIMD, rate control and threading; this is the largest unknown
  (the decoder took 86 min, but its perf work took hours, M9: 4.7 h). Mitigation: the transcode pipeline degrades to copy/remux when the source
  already suits the target; ship CAVLC baseline/main first, CABAC and B-frames after; "real time" is measured on the perf fixtures.
* **R2 Plain-HTTP web app.** A page from `http://192.168.x.x` is not a secure context: no service worker, no SharedArrayBuffer (so no threads
  build), no WebCodecs. The single-thread wasm player still works. Optional self-signed TLS helps only after the user trusts it on the phone.
* **R3 Codec patents and licences.** Shipping an H.264 and an AAC encoder is a legal question separate from code (clean-room helps copyright, not
  patents; many H.264 patents expire by 2027 to 2030, AAC licensing is by Via LA). Human gate before the encoders ship enabled.
* **R4 Device quirks.** TVs differ wildly in UPnP (DIDL variants, byte-range habits, container support); Cast wants specific H.264 profiles and
  MP4/HLS shapes. Expect a long tail found only on real devices; keep a per-device quirk table.
* **R5 Network exposure.** Any listener is attack surface; mitigated by off-by-default, LAN-only, read-only, opaque ids, pairing and limits, but
  it needs a dedicated security review before it ships on by any default (it never does).
* **R6 Cast protocol.** CASTV2 is reverse-engineered and widely implemented but not a public contract; Google can change it. No "Cast Ready"
  certification; the default media receiver is the target.
* **R7 Scope.** Seven features plus two encoders is about two milestones' worth of surface. The order below ships the useful things first.

## 9. Runtime-loadable drop-ins (wasm components) for v1.2: recommendation

**Not worth it for v1.2.** Costs: a wasm runtime in every desktop build (several MB), host-API marshalling for sockets, multicast and threads
(WASI sockets are still young), a second build pipeline, harder debugging, and slower hot paths (the encoders must stay native). Benefit: third-party
plugins, which nobody has asked for and which would need a sandbox policy and a signing story. Keep drop-ins compiled in, switched on at run time.
Cheap insurance: the interface is already message-based and serialisable (section 3), so an adapter that hosts a wasm component behind
`DropIn` can be added later without touching any drop-in. Revisit only when an outside party wants to ship their own.

## 10. Order and estimates (agent hours, one coder; measured against M0 to M11 = about 16 h, M6 decoder 86 min, M10 library 1.9 h, M11 desktop and packaging 85 min, crossfade 63 min, HEVC decoder with conformance about a day)

| 2 | `rvp-net` (HTTP server and client, WebSocket, SSDP, mDNS, private-peer checks) and `rvp-xml` | 4 to 5 |
| 3 | `rvp-mux` and Remux to MP4 (a Server action and a context-menu entry) | 2 to 3 |
| 4 | `rvp-netsource` and WebDAV | 4 |
| 5 | Jellyfin and Subsonic/Navidrome clients (browse, search, covers, streaming, sources in Music/Video) | 5 to 6 |
| 6 | UPnP: server, control point, renderer, Play To sender | 10 to 12 |
| 7 | LAN web server, pairing, phone remote | 6 to 8 |
| 8 | `rvp-enc-aac` | 4 to 5 |
| 9 | `rvp-enc-h264` (baseline/main CAVLC, motion search, rate control, SIMD, threads, then CABAC/B) | 14 to 20 |
| 10 | `rvp-transcode` and its use by the server and Cast (HLS/fMP4 output) | 5 |
| 11 | Chromecast sender | 5 to 6 |
| 12 | Docs, packaging notes, security tests, release | 4 |
| | **Total** | **about 67 to 83** |

Steps 1 to 5 are useful alone and carry the least risk; 6 and 7 come next; encoders (8 to 10) are the long pole and can run in parallel with 6 and 7
if there is a second coder (one at a time per the project rule, so sequentially: about 3 days of agent time for the whole plan, plus the gates).
v1.2 (SMB, radio and podcasts, multi-room, AirPlay) is a separate estimate once v1.1 shows the interface holds: about 25 to 35 h.

**Human and third-party gates (not agent time):** real-device tests (section 7); the legal call on H.264/AAC encoder distribution (R3); a security
review of the listeners before they can ship; Windows and macOS firewall and Local Network prompts checked on real machines; Flathub's review of the
network permission; notarisation for any macOS change; the user's go before each tag. CI minutes are only for preflight and the tag.
